## Adversarial no-go

The receipt dictionaries and `_issue_*` functions live in the same Python
module as the consumer. A hostile caller with arbitrary in-process execution
can call those functions or mutate their registries and mint a self-consistent
production-looking chain. SHA-256 detects accidental or post-issuance changes;
it is not a signature and creates no capability boundary. Therefore the
current mechanism is an **integrity/provenance convention for cooperative
code**, not issuer authentication or hostile-process security.

A second judge demonstrated that `issue_m172_source` accepts a source weight,
covariance, and owner tables not structurally bound to the M179 archive's
weight trace. The function recomputes the M167/M172 algebra for what it is
given, but it does not prove that those inputs came from the same traced layer.
This remains an explicit production-ABI gap.

External signing would repair hostile provenance, but it would add no estimator
information and is outside this contest mechanism. Do not spend the remaining
research window on security theater. The honest repair is to keep these
receipts as consistency checks and make the eventual integrated compiler pass
the archived layer object directly, so source weight, covariance, owners, and
context share one construction path.
